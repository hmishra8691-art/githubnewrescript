# Translation intelligence — languages as copilot actions

*Research-intelligence brief, Phase 3 ("Multi-language & translation intelligence: copilot translation actions, per-market language routing, stale-translation detection and locking"). Built 2026-10-04 on the Intelligent copilot (INTELLIGENT-COPILOT.md) and the existing Localization layer (LOCALIZATION.md).*

## What it does

Languages were already a full system — language versions with a status, a translation table keyed by stable element addresses, a glossary, routing by URL / embedded field / country / rules / browser, audio, and a lint that decides whether a version is *ready*. What was missing was the copilot: asked to "translate the survey into German" it could only say that the Localization panel exists. Now:

- **The copilot translates.** A request about languages brings the TRANSLATION GUIDE and, in the outline, each language version's state, the glossary, the routing, and for the questions the request names (or every question of a block it names) their translatable elements with the existing translation and its status in every language. The model writes the translations itself and returns them as `set_translations`; the engine resolves each target against the survey (`Q5`, `Q5.option:2` or by label, `Q5.row:r1`, `Q5.instruction`, `Q5.scale:low`, `end:complete`, `block:Brand`, `button:next`, `ui:required`, `meta:title`, or the raw key) and checks each text against its source before storing it: a dropped or changed `{{pipe}}` / placeholder, unbalanced or mismatched HTML, an empty text, a do-not-translate glossary term that is no longer there — each is refused *by element and by reason*, the rest is written, and the refusals are shown in Changes. Preferred glossary wordings not used are a warning. Everything is stored as machine translation (`ai`) to be reviewed.
- **Locking.** An approved or reviewed translation is **kept** against a plain `set_translations` ("3 approved translations kept — ask to overwrite them if you mean to"); only `overwriteApproved: true` replaces it, and the replacement is `ai` again. `approve_translations` (or `status: "reviewed"`) locks; the Languages tab offers it as a proposal.
- **Stale detection and the impact loop.** After every proposal the engine marks every translation whose source text changed as **outdated** — its text is kept and still shown, which is better than falling back to the source language — and tells the researcher: *"1 translation is now outdated (de) — the source text changed; ask to re-translate them, or confirm them in Localization."* The Changes panel shows the warning with **Re-translate them in this proposal**, which asks the copilot and chains the re-translation onto the same proposal, so the wording change and its translations are applied as one undoable change. A source edit made in Studio is detected the same way (by the stored source hash) and surfaces in the Languages tab, the Localization panel and the review. `confirm_translations` says an outdated translation still fits (it becomes `edited`, stamped against the new source).
- **Routing in words.** `set_language_routing` takes a country map ("US → en, MX → es, DE → de"), the URL parameter, the embedded field, rules on conditions, the switcher and the fallback; every language named must exist; maps and rules merge by default; the country / rules steps are inserted into the precedence order ahead of browser detection and the respondent's choice, and the insertion is said.
- **Languages and the glossary.** `add_language` (locale from the language library, refused for the source language or a non-code, appended to the deployment's languages), `remove_language` (destructive, drops its translations and audio), `set_language_status` (refused for *ready* / *live* while a blocking issue remains, naming the kinds), `set_glossary` (add / update / remove, removal destructive).
- **Everything stays one localization.** The actions write `def.localization` — the same object the Localization panel edits and the runtime resolves — so nothing is stored twice and the Localization panel shows what the copilot did.

## Principles kept

- **Reasoning is separated from execution.** The model writes words; the engine decides what is storable, element by element, and the researcher applies. The model never writes `def.localization` directly, never a key it was not shown, never a code or a condition.
- **Human in the loop.** Every translation arrives as a proposal in Changes; approval is a researcher's act and a lock; a source change asks, it does not silently leave the German behind or silently rewrite it.
- **Nothing duplicated.** One localization object, one lint, one target grammar for the model and the Languages tab; the Localization panel is still where translations are edited by hand.

## Tests

- engine `localizationActions.test.ts` (5): the target grammar; the refusals; add → translate a block → approve → kept → overwritten → *ready* refused → removal destructive; the outdating loop with its warning, confirmation (stored and detected-only), re-translation and the review's findings; routing in words (merging, replacing, the order) with `resolveLanguage` following it; the order of language actions within a batch. **Mutation-checked: 70 mutations, 69 caught** — 17 first survivors closed with tests, which also found a real bug (`merge: false` was dropped at the gate, so a routing replacement always merged); the one survivor (localization ranked with the structural actions instead of after everything) is behaviourally equivalent because the sub-ranks still order it after the structure.
- studio `copilot.test.ts` (+1): the intent, the block focus, the outline's languages block with existing translations and the missing one, the guide, the vocabulary, the gate. **Mutation-checked: 10 / 10** (prompt, outline, the guide sent only on translation turns).
- browser `scripts/translation-copilot-test.mjs` (10): the copilot's actions through the fake provider with the refused entries shown; the Languages tab and Approve; kept vs overwritten; a copilot wording change → outdated warning → re-translation chained into the same proposal; a Studio edit → outdated → Confirm; routing; the Localization panel sees the same language; the review; the turn route recognising a translation request and sending the languages and the guide. **Mutation-checked against the Studio surfaces: 10 / 10** (route, Changes panel offer, Languages tab counts and actions).

## Not done

- The model's translations are not **machine-checked for meaning** beyond structure (pipes, HTML, glossary); a wrong translation that keeps the structure is stored as `ai` for review, as a human translator's would be.
- **Audio** is untouched by the actions: a re-translated element's recording is reported stale by the existing lint, not regenerated.
- `remove_language` and `set_language_status` are not offered as buttons; they are asked for in words (and the status change is refused while anything blocks).
