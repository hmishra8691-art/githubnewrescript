Logic Engine Compatibility Audit

Display Logic, Validation Logic and Masking Logic audited against the three master test questionnaires — 437 scenarios, deduplicated to 152 distinct capabilities, each checked in source and then driven through the real engine rather than taken on trust.

Nine of the fourteen were not missing features but silent wrong answers — rules the builder accepted, saved and displayed, which then evaluated to the wrong thing at runtime with nothing on screen to say so.

What was broken

Every item here was reproduced against the real engine before being changed, and is covered by a test that fails without the fix. Severity is about respondent-visible consequence, not effort.

Critical A hidden question could screen a respondent out Fixed

Skip logic ran over every question authored on a page, not the ones the respondent was actually shown. A question hidden by display logic has no answer, so a rule like Q2 unanswered → terminate fired for exactly the respondents for whom Q2 was correctly hidden. Confirmed by driving the flow engine: the respondent was returned endStatus: "screened" on a question that never rendered.

packages/engine/src/flow.ts — firstTriggeredSkip now iterates visibleQuestions()
Critical Masking every option away produced an unanswerable blocking page Fixed

When a mask, a carry-forward or a List Fill resolved to nothing, the question stayed on the page with an empty list and required still enforced: the respondent was told to answer and given nothing to answer with, with no way forward. Requiredness is now suppressed only when a question that had items has lost all of them — covering M156 (empty source), M157 (zero rows) and M158 (zero columns) at one point. Ordinary required questions are untouched, which is asserted directly.

packages/engine/src/validate.ts — hasNoAnswerableItems()
Critical The Universal Logic Engine's validation mode was unreachable in the UI Fixed

Condition-tree validation is implemented for every question type in the engine, but the properties panel offers exactly the kinds a question's variant declares — and no variant declared condition. So for any question carrying a variant, which is every new question, the feature could not be selected at all. Worse, switching variants deleted any such rule already saved. Four kinds that are type-agnostic in the engine — required, condition, custom_expression, custom_script — are now declared once and unioned in, instead of being restated per variant and silently forgotten.

packages/schema/src/variants.ts — UNIVERSAL_VALIDATIONS, allowedValidationKinds()
Critical Auto punch overwrote whole answers on image questions Fixed

Two hand-maintained lists decided whether a question holds one code or many. One omitted image_select — so punching one took the single-answer branch and replaced the respondent's entire selection with a single code. The other asserted it was scalar, so a response filter on it emitted a containment test that could never match and suppressed the engine pass that would have got it right. Both now ask the schema's response model, which knows image_select backs both a single- and a multiple-choice variant.

packages/engine/src/setExpression.ts, responseFilter.ts — isMultiValuedQuestion(), isScalarAnswerQuestion()
Major No date arithmetic existed at all Fixed

The expression language had thirty-four functions and not one that understood a date, so ten validation requirements (V041–V050) had no expressible form: age on the day of the survey, no future dates, expiry, end-after-start, and both relative windows. Added TODAY, AGE, DATEDIFF, DATEADD, DATE, YEAR, MONTH, DAY — in the shared function table, so a calculation, a display condition, a mask and a validation rule all spell them identically. Ages are calendar-aware and compared in UTC whole days, so they do not flicker by the respondent's timezone.

packages/engine/src/calc.ts — AGE("1990-06-15") → 36
Major Comparing one question against another was silently impossible Fixed

Every right-hand side was a literal. The obvious spelling of a cross-question rule — pick Q5, pick >, type Q6 — compared Q5 against the two characters "Q6" and was false forever, with no error. This one gap blocked confirm-email (V022, V112), end-after-start (V045), min-vs-max (V084), subset and empty-intersection (V068, V069), dynamic exact count (V070), sum-within-budget (V082) and Q94 != Q90 in the display document. A comparison value can now be another question's answer, resolved through the same lookup the left-hand side uses, reachable from the visual builder, round-tripping through the expression tab, and visible to the dependency graph so it re-fires live.

packages/schema/src/conditions.ts — QuestionValueRef · evaluate.ts · logicExpression.ts · dependencies.ts · ConditionBuilder.tsx
Major Matrix cell validation and row rules were accepted and discarded Fixed

A matrix answer is an object keyed by row, so a min_value rule written at question level was handed that whole object — Number({…}) is NaN, and the rule passed. The panel offered min/max for matrix_numeric regardless. Per-row rules failed from the other direction: the canvas wrote row.validation for any matrix and only the two list types ever read it back. Both now run the same checkScalarRules per cell that every other shape uses, over visible rows only — which is also what V099 asks for.

packages/engine/src/validate.ts — per-cell and per-row rules for matrix types
Major Every time-of-day comparison was false Fixed

A time question stores a bare clock value, and the date parser rejected it outright — so "between 09:00 and 17:00", the only thing a time question exists to be asked, never matched. Clock times now parse, and the five ordering operators put their operands on one comparable scale, so >, <, ≥, ≤ and between work on dates and times as well as numbers. Deliberately all-or-nothing: a date compared against a plain number stays false rather than being coerced into a timestamp.

packages/engine/src/evaluate.ts — toTime(), comparableOperands()
Major Whitespace satisfied a required question Fixed

A single space passed required everywhere and arrived in the data file as an answer (V009). Emptiness is decided in one function, so trimming there covers scalars, array members and grid cells at once.

packages/engine/src/validate.ts — isEmpty()
Major Matrix column conditions never matched Fixed

Naming a column without a row indexed a row-keyed answer map by the column id and always found nothing — while the builder went on offering the column picker. A column with no row now means "this column, across every row", which is the natural reading and the one the display document asks for ("any row rated Often or Always"). The three matrix shapes are handled distinctly: a single-response row stores the column it chose, so only rows that chose it count.

packages/engine/src/evaluate.ts — column-only drill-down
Major A broken expression turned a validation rule into a no-op Fixed

V131 spells its rule with REGEX(…), which did not exist; the unknown-function error was swallowed and the rule passed everything. REGEX/MATCHES now exist as functions alongside the matches operator the visual builder already had.

packages/engine/src/calc.ts
Latent Three more duplicate lists, one already stale Fixed

The expression parser kept its own copy of the function names and had already fallen behind by the whole date family, so a rule the evaluator could compute would have been rejected at parse time as an unknown function. It now derives from the single source, as the codebase's own comments say such lists should. The dependency graph was likewise blind to expr sources, to count … where clauses and to right-hand question references — rules that authored correctly but could fail to re-fire when their input changed on the same page.

What is still open

Each of these has a single identified cause. The first group is small and mechanical; the second needs a new mechanism, not a removed restriction.

Removable restrictions — no new mechanism needed

  • Always-show is coupled to the empty-source setting. Whether a protected "Other" survives a mask depends on a field that describes an unrelated concern, so the same option can be kept or dropped for a reason the author never chose. These should be independent settings.
  • Preselect and disable mask actions do nothing. They are stored, authored, exported — and no consumer applies them. Either wire them or withdraw them from the picker; leaving them offered is the failure mode this audit exists to catch.
  • The masking source picker hides scalar questions. The engine reads a hidden, embedded or numeric variable as a source perfectly well; only the dropdown filters them out.
  • The operator allow-list raises hard errors on rules the evaluator handles. Numeric comparison of a matrix cell, and the three contains operators on a ranking answer, are implemented and then rejected by a lint error.
  • Nested-loop masking is blocked by one missing scope field on the loop-item set leaf — conditions already have it.
  • The when gate on validation rules has no editor, so conditional requiredness has to be re-spelled as a condition rule.
  • Ranking selection bounds are offered by one panel and denied by another.
  • Column masking records no debug trace, so M150's "explain why this won" is answerable for options and rows but not columns.

Genuine gaps — these need building

  • Cell-level masking (M073, M078) needs a fourth mask dimension plus renderer support.
  • Iteration history — "hide items already used in previous iterations" (M128) — needs a consumed-set in response state that does not exist.
  • Aggregates across loop iterations (V130) need a rollup hook; validation is currently invoked per iteration with no page-level pass.
  • A predicate leaf in the set language would turn numeric-band, text-match and expression-driven masking from workarounds into first-class masks. This is the single highest-leverage remaining item for masking: one schema node closes six scenarios.
  • Rank uniqueness (V095, V101, V110) has no check anywhere.
  • Randomised-block assignment must be recorded as a variable before any rule can read it.
  • Flow position needs a new source kind and a position on the evaluation context.
  • Live validation clearing — errors persist until the next submit even after the respondent fixes the input. The dependency graph needed to do this incrementally already exists and is simply not wired to validation.
  • Answers to questions that later become hidden are retained and exported. There is no clear-on-hide policy and no setting for one; a data file can contain answers the respondent's final path says they never saw. This is a decision to make, not only code to write.

Test evidence

Nothing here was accepted on the strength of reading the code. Each fix was reproduced first, then re-run.

  • Three severe defects reproduced against the compiled engine, and a guard asserting the required-suppression is narrow — ordinary required questions on options, text and matrix all still block.
  • Nineteen capability checks covering cross-question comparison, its round trip through the expression language, confirm-email, date chronology, dynamic age, no-future-date, relative windows, time-of-day ranges, matrix column conditions, and a condition-tree validation rule enforcing an inverted date range end to end.
  • 771 engine unit tests, unchanged and passing.
  • The full monorepo — typecheck, build and test across all twelve workspace projects — clean.
  • Targeted browser suites over the changed surfaces: validation conditions, count logic, the logic builder, save integrity, option logic, matrix auto punch and masking.
  • The full 61-suite browser corpus against a live Studio and runtime.
Audited against the Display Logic, Validation and Masking master test questionnaires.
