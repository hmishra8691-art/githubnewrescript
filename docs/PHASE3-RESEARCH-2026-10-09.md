## What was built

**Structured hypotheses (`packages/engine/src/hypotheses.ts`)** — `parseHypothesis(text)` reads type (causal / association / difference / descriptive), direction (positive / negative / difference / none), the sides ("X drives Y", "Y depends on X", "X is positively related to Y", "X affects Y", "X differs by Y"), mediation and moderation ("T mediates the effect of X on Y"), and group differences ("women are more satisfied than men" → group women, lower men, dependent satisfied; "younger respondents are less satisfied" → the low-end subject turns the direction round, as the verdicts always read it). The first verb decides and the object stops at a second clause. `structuredHypotheses(def)` merges what is recorded over what is parsed, says which fields came from where, and resolves each side to a construct (`constructFor`: the name whole, else every word of the shorter side carried by the other as families; a tie names neither). The analytics verdicts' `hypothesisDirection` now delegates to this parser and a recorded direction overrides the words.

**Actions** — `set_hypothesis` (a side that names a construct must name one the design has; a word or two off is corrected to it; a no-op is refused), `add_hypothesis` with an optional reading; `remove_hypothesis` keeps the readings aligned; `set_research` carries the readings by statement text when the list is replaced, and records or keeps `researchQuestions`, `kpis` and `audience`. The prompt documents `set_hypothesis` and the new fields; the outline shows each hypothesis's reading in braces and the audience, questions and KPIs, so the model corrects a reading when the words say otherwise and writes for the audience.

**The graph (`dependencyIndex.ts`, `impact.ts`, `nlIntent.ts`)** — a hypothesis reads the constructs on its sides and the questions tagged with it; a plan item that serves it reads it; a KPI reads the question (or derived variable) its variable comes from. `impactOf` on a deletion reports each hypothesis the question measures ("changes" when it would be left unmeasured, "informs" when other questions remain) and each KPI read from it ("breaks"). `objectFor` resolves "H1", "hypothesis 2", "the third hypothesis" and a KPI by name, so the dependency questions answer them; "which questions measure H1" is `reach(H1)` in flow order, with the constructs no question measures and the planned analyses that serve it.

**Relevance (`relevance.ts`)** — every placed data question scored by what it serves (a hypothesis through a tag or a construct: +4, a construct: +2, a KPI: +4, the plan: +2, the screener: +3, a demographic cut: +2, the objective's words: up to +2) and listed with what reads it at run time. The tier is the design's: essential (hypothesis, KPI, screener), supporting, unconnected. `removalSet` removes the unconnected questions nothing reads, lowest first; with a target ("to 6 questions", "by 4", "to 3 minutes") it reaches into the supporting ones, lowest first, and never into the essential; an unconnected question read by logic is held and named with the logic. With no research design at all the sentence is refused — nothing can be called unnecessary against nothing. `coverageReport` reads the same scoring for the generation gate.

**Recognisers** — *make the questionnaire shorter [without losing …]*, *shorten / trim / cut the survey [to N questions | by N questions | to N minutes]*, *remove the unnecessary / irrelevant questions*, *delete the questions not related to the research objective* → the removal set as `delete_question`s with the impact and the essential questions named; *which questions could be removed / are the least important* → the ranking in three sections; *set the audience to …* → `set_research`; *make this survey more suitable for X [and remove unnecessary questions]* → the model, with "Record the audience" and "Remove the unnecessary questions" as the engine's executable steps when the model has nothing. A sentence with an "and" clause that is one request is read whole before it is split into commands.

**Studio** — the Research design editor shows each hypothesis's reading as a button (the words' reading by default), opening type / direction / expected effect / status selects and the sides with the constructs as suggestions; sections for research questions, KPIs (name, variable, measure, target, direction) and the audience (description, language level, characteristics). The Analysis tab shows the reading beside each hypothesis's coverage. The Research tab's document cards have "Use in the research design" (`lib/copilot/mergeDoc.ts`), disabled when the design has everything. A generated proposal's card carries a Coverage line.

**The coverage gate (turn route)** — after the gate and the refusal repair, a generation's clone is checked with `coverageReport`; when something is loose and the turn was not cached, the model is asked once more with its own answer and the loose ends named, to answer with the same actions plus the tags, construct links or questions that connect them; the second answer is used only when it covers more and accepts no fewer actions. The report travels with the proposal either way.

Existing tests changed on purpose: `impact.test.ts` now expects the hypothesis measured only through Q7 among a deletion's dependents (the summary names eight, so the language moved into "and N more"); `copilot.test.ts` raises the prompt-size cap from 13,800 to 14,600 characters for the `set_hypothesis` line and the new research fields (the outline check expects a hypothesis's reading in braces); `scripts/phase1-reliability-test.mjs` asks the wallet model for a friendlier tone instead of a shorter questionnaire, because the engine now reads "make the questionnaire shorter" itself.

One regression found by the full browser corpus and fixed: `scripts/ux-copilot-test.mjs` read the AI change history the moment the applied note showed and found the entry reading "Applied …" instead of "Created …". The record of an applied change (what was created, modified and removed — the page's own diff) joined the history only after the server had numbered the change, a round-trip later, so for that time the entry showed the server's list and ⌘Z was not watching it; the suite had passed on timing alone. `commitApplied` now records the change the moment the store takes it and patches the number in when the server answers; the suite asserts the record is there when the applied note is (and fails without the fix).

Mutation checks: engine 36 mutations, all caught after three tests were strengthened and one redundant filter removed; Studio 11 mutations through the browser suite, all caught after one check was strengthened (the audience fallback's second choice).
