### A11. What must NOT be done (destructive / breaks invariants)

1. Never `UPDATE survey_versions.definition` (trigger `survey_versions_immutable` refuses; deployments and responses are pinned by `version_id`). Any JSON shape change is a new optional key with a default, applied on read, never a rewrite of stored versions.
2. Never rewrite `responses.answers` in a migration. Use the row-locked RPCs (`rescript_update_response` with revision, `rescript_set_answer_transcript`) from a route, with `response_edits` rows.
3. Never `DROP COLUMN` (0017 states the rule: "dropping a column is the one schema change that cannot be undone by writing more SQL"); keep deprecated columns (e.g. `project_invitations.token`, `media_objects.storage_provider='supabase'` rows).
4. Never add `UPDATE/DELETE` to `usage_events`, `wallet_ledger`, `credit_transfers` (immutability triggers); corrections are reversal rows.
5. Never add a permissive policy to a deny-all table (login_attempts, password_resets, auth_handoff_codes, user_ai_credentials, listfill_*, response_edits/reviews/counters, media_*, interview_*); never `grant` on `user_ai_credentials`.
6. Never `create or replace` a set-returning function whose OUT columns change — `drop` first and **re-apply the 0026 revokes/grants** (0043 shows the 403 that follows a forgotten grant).
7. Never widen `rescript_resolve_share`'s return type (0014 explains the live-link dependency); add a sibling function.
8. Never make `increment_quota_counts` or `rescript_allocate_listfill` read-then-write in application code; the atomicity is in the statement.
9. Never add a NOT NULL column without a default to `responses`/`respondents` (the runtime inserts and retries without new columns — session.ts:33–50 — a required column would break every session).
10. Never re-run 0025's wallet sweep by hand on a database where owners have changed since; it is idempotent only via `retired_at`.
11. Never enable `anon` EXECUTE on any `rescript_*` function (0026 header documents `rescript_login` as a full auth bypass).

## PART B — RUNTIME (code-level)

### B1. Session persistence and resume

- Row minted by `POST /api/session/start` after the runner mounts (`Runner.tsx:448–525`), not at server render. Session id = 32-hex UUID (`session.ts:97`), stored in **localStorage + sessionStorage** under `rescript:session:<mode>:<surveyDbId>` with a timestamp; expires after `RESUME_MAX_AGE_DAYS = 30` (`lib/resume.ts:32,60–95`). A `?r=<sessionId>` link overrides the stored pointer (resume email on another device).
- Resume is honoured only when the row is the same survey, same environment, `status='in_progress'`, not deleted (`start/route.ts:68–102`); the server returns `saved.{answers,calculated,embedded,flags,stepIndex}` and the runner replays through `resumeAt(def, state, counts, saved.stepIndex)` (`Runner.tsx:891`; engine `resumeStep.test.js`: **34/34 pass**, executed).
- Every page advance persists the **whole state** (`persist`, `Runner.tsx:132–164`); before the request the snapshot is cached in `localStorage` `rescript:pending:<sessionId>` and cleared on ack (`Runner.tsx:1353–1370`); on boot a pending cache newer than the server copy is merged over it (`Runner.tsx:494–505`). Final save is awaited, retried 3× with backoff, and the thank-you/redirect only shows after the server acknowledges (`persistFinal`, `Runner.tsx:166–177, 1322–1341`); failure shows a Retry card (`1441–1446`).
- **Back navigation does not persist** (`handleBack`, `Runner.tsx:1390–1408`: `goBack` + telemetry only; no `persist`). `step_index` on the server stays at the furthest page; a reload after Back resumes at the furthest page, and any edits made on the earlier page are only saved when Next is pressed there. (`moveForward`/`goBack` throw on non-terminating flows → `setFatal`, which is correct.)
- Re-entry by the same respondent: `createSession` for unique-link/invitation mode refuses only terminal statuses when `allowRetake=false` (`session.ts:166–167`); a respondent whose row is `started`/`in_progress` arriving **without** the local pointer or `?r=` (other device, cleared storage) gets a **second `responses` row** for the same `respondent_id` (`session.ts:148–192`, no "existing in_progress for this respondent → resume" branch). Open-link mode has no respondent identity at all, so re-entry on another device always starts a new row (by design).

### B2. Submit API server-side validation — see A9 and RUNTIME-01

`/api/session/save` does not re-run validation, flow or quota logic. It trusts `status` (whitelisted to the five values), `stepIndex`, `answers`, `calculated`, `embedded`, `flags`. Only `telemetry` is sanitized (`sanitizeTelemetry`, lines 206–252). No body-size cap in the route (Vercel's 4.5 MB request limit is the only bound).

### B3. Quota increment atomicity

The increment itself is atomic (`insert … on conflict do update set count = count + 1`, 0006/0010) and is executed only by the winner of the `update … where status='in_progress' … select("id")` compare-and-swap (`save/route.ts:89–114`), so double-counting from a double-submit is prevented. The **cap** is not atomic (SCHEMA-01). The 2-argument fallback at `save/route.ts:130` calls the same 3-argument function (the 2-arg overload was dropped in 0006:273), so a transport error after commit would count twice — P3.

### B4. Completion / termination / redirect

Engine `advance` returns `endStatus` (`complete|screened|quota_full|terminated`) and `redirectUrl` (`packages/engine/src/flow.ts:501,587,597,607`); the runner runs `on_complete` scripts, saves with `completed:true`, clears the resume pointer, then redirects (live mode only; `_blank` honoured) (`Runner.tsx:1313–1341`). `redirectUrl` templates are resolved by `resolveUrlTemplate` with per-token percent-encoding; a leading URL-typed embedded field is used verbatim but `checkUrlValue` restricts it to `http(s)://` with a hostname (`packages/engine/src/embedded.ts:41–52`), so `javascript:` cannot reach `window.location.href`. Open redirect to an attacker-chosen host via `?ed=` is possible by design (panel return URLs) — documented warning at author time. List Fill claims are confirmed on `complete` and released on any other terminal status (`save/route.ts:146–150`).

### B5. Partial responses

Stored as `responses.status='in_progress'` with `step_index`, `answers`, `last_saved_at`, `updated_at` (trigger). Reporting treats them as partials (`rescript_field_pulse`, `rescript_field_positions`). Nothing ever closes an abandoned partial: no expiry, no status change, and List Fill `allocated_count` stays claimed until `rescript_recount_listfill`/delete (0007 header acknowledges). Analytics default dataset is `complete` only (`DatasetSpec.statuses` default), so partials do not pollute results, but quotas and List Fill caps can be held by ghosts.

### B6. Mobile rendering strategy

CSS-only, max-width media queries in `packages/renderer/styles/*.css`; no JS viewport branching except `.rs-viewport.mobile/.tablet` classes for the Studio preview and author-level responsive overrides in `branding.ts:185–186` (641–1024 / ≤640). Breakpoints in use: **420, 440, 460, 480, 520, 560, 640, 900 px** (8 distinct values across 21 files; e.g. matrix stacks at 560, slider matrix at 520, choice grids collapse at 640→2 cols and 440→1 col). Matrix/Likert tables convert to stacked cards ≤560 (`matrix.css:272–284`), sum-matrix stays a scrollable table with narrowed inputs ≤520. Touch targets: option rows ≥44 px (`questions.css:343`), native `<input type="range">` sliders. `prefers-reduced-motion` and `prefers-contrast: more` honoured. Next.js injects the default `width=device-width` viewport meta (no override in `apps/runtime/app/layout.tsx`). **BROWSER-REPRO NEEDED** for actual layout at 360/390/768 px.

### B7. Accessibility (renderer grep)

- Single/multi choice: `role="radiogroup"` + native radios/checkboxes (`QuestionRenderer.tsx:411–458`), 12 keyboard handlers in `singleSelect.tsx`; cards/carousel/dragdrop/gamified/list/datetime have aria + key handlers (table in scratch). Question wrapper carries `role="group"`, `aria-describedby`, `aria-invalid`, `aria-required` (`QuestionRenderer.tsx:693, 2786–2811`).
- **Default `matrix_single`/`matrix_multi`**: native `<input type="radio"/"checkbox">` inside `<td>` with **no `aria-label`/`aria-labelledby`** and header `<th>` without `scope="col"` (`QuestionRenderer.tsx:1528–1566`); screen readers announce "radio button 1 of 5" with no row/column name. The Likert/rating-matrix variants do label each control (`matrix.tsx:398–400, 487–489`) and use `scope="col"` (`matrix.tsx:454`) but implement `role="radio"` as independent `<button>`s (Tab reaches each; no arrow-key radiogroup navigation).
- Slider: native range inputs with `aria-label`/`aria-orientation` (`slider.tsx:97–151`).
- `focus-visible` styles present (5 rules). Live regions: `role="status" aria-live="polite"` on UX messages and media gate.

### B8. Scripts — post-unification state

Three script surfaces exist after the unification (`docs/SCRIPT-PIPELINE-2026-10-15.md`):

1. **UX scripts** (`def.ux.behaviors[].script`) — `UxLayer.tsx` creates one `<iframe sandbox="allow-scripts" srcdoc>` per script per page (lines 303–309) with CSP `default-src 'none'`; the frame catches every error (`uxSandbox.ts:70–73, 96–97, 342, 347`) and reports it as an `error` command → `console.error` + inspector (`UxLayer.tsx:289–293, 361`). Loops are bounded by `guardScriptLoops` (100 000 iterations per entry). Host-side `onMessage` (`UxLayer.tsx:321–364`) runs outside React render/commit; `DomBridge.apply` wraps each op in try/catch (`uxDom.ts:150–165`). A script cannot write answers (`value/checked` not in the attribute allow-list, `uxDom.ts:55–58`). On page leave: 150 ms grace, dispose + undo (`UxLayer.tsx:312, 385`). **No path from a UX script exception to React render or to the Next handler** — verified by reading; the only React-side code is the `useEffect` that calls pure engine validators (`validateUxScript`, `guardScriptLoops`), which would only throw on an engine bug.
   - A UX script **can** block navigation *by design*: targets `next`/`submit` resolve to `[data-rs-button="next"|"submit"]` (`engine/ux.ts:119`), and `hide`, `disabled`, `hidden` are allowed effects/attributes (`UxLayer.tsx:351–352`, `uxDom.ts:56`); `reassert` re-applies them after every React re-render (`uxDom.ts:307–312, 322`). A buggy script that disables Next and never re-enables it strands the respondent on that page (the undo only runs when the page is left). The CSS gate warns about `pointer-events:none` on buttons (`ux.ts:348`) but nothing refuses `disabled`/`hidden` on the navigation buttons.
2. **Logic scripts** (`def.scripts[]`, events on_load/on_change/on_validate/on_submit/on_complete) — `packages/engine/src/scripts.ts:288–305`: `new Function` on the **main thread**, "sandboxed" by parameter shadowing of 28 globals (lines 39–46). Exceptions are caught (`result.failed`) so a throw cannot break Next; `error()` calls become blocking validation errors (by design). **No loop guard and the shadowing is escapable** — repro below.
3. **Legacy `customJs`** — migrated to UX scripts by `migrateLegacyCustomCode` in the Runner and Studio store; `custom_component.customJs` remains unsandboxed by design.

Repro (`docs/audit-2026-10-16/repro/schema-runtime/script-escape.mjs`, run against `packages/engine/dist`):
```
1 throw caught -> boom
   script log: function        <- typeof globalThis.setTimeout reached via [].constructor.constructor('return globalThis')()
   script log: function        <- typeof globalThis.fetch
2 escape failed? -> no error (escape succeeded)
3 while(true) -> KILLED by watchdog after 3026ms (no loop guard)
```
Expected: a logic script cannot reach `fetch`/`window` and an endless loop is stopped. Actual: both reachable; `while(true)` in an `on_validate`/`on_submit` script hangs the respondent's tab on Next (the handler runs synchronously before `advance`, `Runner.tsx:1157–1158`).
