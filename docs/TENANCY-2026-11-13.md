# Tenancy groundwork: a big client in a database of its own (2026-11-13)

**What this is:** the groundwork that lets a big client be given a database of its own later without a rewrite. **Nothing
behaves differently today.** Every client still uses the one primary database, and routing is locked in code until
the wiring is finished.

## What exists now

| Piece | Where | What it does |
|---|---|---|
| The routing core | `packages/storage/src/tenancy.ts` (`@rescript/storage/tenancy`), 4 tests | Reads and validates the configuration; `resolveDatabase(scope)` returns which database (url + key) a piece of data lives in. Today it always returns the primary. |
| One way to get a client | `apps/{studio,runtime,interviews}/lib/db.ts` | `dbFor({ kind: "customer", customerId })` for a client's data, `platformDb()` for sign-in, workspaces and billing, `customerDb(id)` as shorthand. `supabaseAdmin()` and the Studio's `supabaseService()` now go through it (still the primary). |
| Where every table lives | `supabase/tenancy/tables.json` | 175 tables: 36 **platform**, 121 **customer**, 15 **shared** (cross-client by design), 3 **review** (open questions). Drafted from the live schema, corrected by hand. |
| A guard that keeps the road open | `scripts/tenancy-audit.mjs` (part of `pnpm audit:code`) | (1) A new table must be classified. (2) Direct `supabaseAdmin()` / `supabaseService()` calls may only go down: 272 Studio, 35 runtime, 69 interviews today (`scripts/tenancy-baseline.json`). (3) From 0097 on, every migration must record itself in `schema_marks`. |
| Every database on the same migrations | `scripts/tenancy-migrations-status.mjs` (read-only) | For each configured database, compares its `schema_marks` with `supabase/migrations` and names what is missing. |
| Migration marks backfill | `supabase/migrations/0098_schema_marks_backfill.sql` (**not applied**) | 0093–0096 never wrote their mark; this records them, but only where their objects exist. |

## The configuration (read and checked today, active later)

```
RESCRIPT_TENANCY=single                      # "routed" is refused (logged) until the wiring is finished
RESCRIPT_DATABASES=acme                      # extra databases, by id
RESCRIPT_DB_ACME_URL=https://….supabase.co
RESCRIPT_DB_ACME_SERVICE_KEY=…
RESCRIPT_TENANT_DATABASES=<workspace uuid>:acme
```

Mistakes are reported as `[rescript:tenancy] configuration problem …`: an unknown id, a missing key, a database
pointing at the primary, a client mapped twice. A mapped client in `single` mode is reported as inactive. Setting
`routed` early keeps everyone on the primary. A half-wired router would split a client's data across two databases,
so the lock stays until the wiring is done.

## The rule for new code (from today)

- A client's data (surveys, responses, quotas, media, reports): `dbFor({ kind: "customer", customerId })`.
- Sign-in, people, workspaces, billing, the survey-link directory: `platformDb()`.
- New tables are added to `supabase/tenancy/tables.json`.
- New migrations end with their `schema_marks` row.
- Avoid one query that joins two clients' data. Cross-client features (fraud intelligence, the recruitment
  exchange) read the **shared** tables.

## What remains before routing can be turned on (the wiring)

| Step | Work | Estimate |
|---|---|---|
| 1. The directory | Keep, in the primary: workspace → database, and survey → workspace (`deployments` and `surveys.customer_id` already hold most of it). The respondent app resolves `/s/<client>/<study>` there first. | 3–4 days |
| 2. Respondent routing key | A save carries only `sessionId`. Either put the database id in the session token, or route by the survey id the runner already sends (`surveyDbId`) and verify the session exists in that database. | 2–3 days |
| 3. Migrate the call sites | 376 direct calls to `dbFor` / `platformDb`, by table class (`tables.json`). Start with the respondent path (runtime: 35). The audit's baseline drops as you go. | 2–3 weeks |
| 4. Shared tables | Fraud, identity and recruitment tables stay central; client databases write their signals there. Decide the 3 **review** tables (`audit_logs`, `notifications`, `sample_allocations`). | 1 week |
| 5. Cron jobs per database | Notifications, expire-partials, billing reservations and the other crons loop over the configured databases. | 3–4 days |
| 6. Migrations on every database | Run `supabase db push --db-url <each>`, then `tenancy-migrations-status.mjs` must pass for all. | 1–2 days |
| 7. Moving a client | Copy one workspace's rows (by `tables.json`, client class only) into its new database. UUID keys mean no collisions. Then switch its directory entry. | 1 week |
| 8. Unlock | `ROUTING_WIRED = true` once the runtime and interviews direct counts are 0 and the Studio's client-data paths are routed. Then a staging test with two databases. | 2–3 days |

The total is roughly **5–8 weeks**, much of it in step 3, which can be done gradually without changing any
behaviour.
