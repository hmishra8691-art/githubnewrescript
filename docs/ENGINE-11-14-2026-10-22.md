# Engine items 11–14: per-item guides, readiness at action time, design repair, script structure (2026-10-22)

Engineer G4. Four weaknesses of the Intelligent Mode engine, fixed and tested. No migration, no new dependency. One
optional environment variable (`COPILOT_ITEM_GUIDES=off`, a rollback switch).

| # | Weakness | What was wrong | Now |
|---|---|---|---|
| 11 | Every staged item carried every guide | Each item call of a build sent all the action guides the brief named (~40k characters), whatever the item was | Each item gets the guides it needs, in a fixed order, with a shared core block. Characters sent fall by 41 %; cache reads still happen on 12 of 12 item calls |
| 12 | Analysis-plan actions with missing inputs were accepted | The copilot stored a plan item the readiness rule calls "not ready". Data Analytics then showed it as invalid | The engine's action gate applies the same rule (`plannedItemReadiness`). It refuses the item, naming the missing role or variable; the repair call fixes it |
| 13 | Refused MaxDiff / conjoint actions were never repaired | A design refused at the gate (`create_conjoint … needs the attributes`) never reached the repair call. Infeasible designs got no help | The repair call covers gate-time and apply-time refusals of every design action. Where exactly one correction exists, the Studio makes it itself. A design that is still refused is reported plainly in the reply |
| 14 | Script checks were regular expressions | Duplicate behaviours were found only on identical text. An overlay written with other spellings got through. The popup's "Close" label was English only | A tokenizer and reader for the sandbox's scripts. Duplicates are found by what the scripts do. Overlays are detected in any spelling. Popup words are localised, right to left included |

## 1. #11 Per-item guide selection

**Before.** In a staged build, each item call carried every guide the brief named: analysis, translation, quota,
List Fill, methods, findings, research, qualitative, reporting and, from today, integrations. That came to 39,768
characters per item on the benchmark brief. A "screening block" item was sent the MaxDiff, qualitative and reporting
guides.

**Now** (`apps/studio/lib/copilot/guideSelect.ts`, used by the copilot route):

- **The core.** Every item of a build gets the guides it always writes from. In a generation that is the ANALYSIS
  guide, because every question gets its analysis tags. In a look-and-behaviour build it is the UX guide. The core is
  one cached block, the same bytes on every item.
- **Each item's own guides.** These are read deterministically from the item's kind, title, detail and objects, and
  from its *own* brief section (the best-matching passage, not the context passages that name every method).
  - A design item gets the research guide.
  - A screener in a build with quotas gets the quota guide.
  - An item (or its section) that names a MaxDiff or conjoint gets the methods guide.
  - Likewise for List Fill, languages, the look, qualitative work, AI interviews, panels and alerts.
  - Findings and reporting go only to an analysis or output item. A block of questions *about* reporting does not
    get them.
  - The "why" for each guide is reported.
- **Fallback.** An item nothing can be read from (kind "other", no signal) gets the build's whole set, so it never
  gets less than before.
- **A miss** is an action whose guide was not sent, for example a MaxDiff proposed by "Add the brand questions":
  - The engine's gate judges the action as always.
  - The route logs it: `[rescript:copilot] guide miss …`, and `context.guideMisses`.
  - A refused action goes to the one repair call, **with the missing guide added**. Staged builds now get that repair
    for design, analysis-plan and guide-miss refusals.

**Prompt-cache order** (`apps/studio/lib/aiPromptCache.ts` `copilotCall`). The system blocks now run from the most
stable to the least stable:

1. the system prompt;
2. the research context and the availability note;
3. the core guides;
4. the item's own guides.

That is at most 4 blocks, which is Anthropic's breakpoint limit. A different guide set rewrites only the last block,
so the prefix (system, context, core) is read from the cache by every item. Two items that need the same set send
identical bytes. The extra blocks now come before the guides for ordinary turns too, because they are the more
stable part.

**Measured.** `node --experimental-strip-types --no-warnings scripts/ai-context-benchmark.mjs`:

- The same 23,867-character brief, the same 12-item plan, built three ways.
- The prompt cache is simulated block by block, Anthropic's way:
  - every block is a breakpoint;
  - a call reads the longest prefix written within 5 minutes and writes the rest;
  - the clock is 40 s for the plan and 50 s per item.
- Priced at claude-sonnet-4-6, cache read 10 %, cache write 125 %.
- Output is assumed equal in every run: 2,500 tokens for the plan and 3,000 per item.

| | BEFORE (brief in every item) | CONTEXT (10-18) | ITEMS (now) |
|---|---|---|---|
| Characters sent, 13 calls | 1,025,431 | 900,924 | **529,095** (−41.3 % vs CONTEXT) |
| Guides per item call | 39,768 | 39,768 | **10,342** |
| Input tokens | 257,142 | 226,015 | **133,057** (−41.1 %) |
| Item calls that read the cache | 12 / 12 | 12 / 12 | **12 / 12** |

| Charge with prompt caching | $2.1910 | $1.7939 | **$1.7128** (−4.5 %) |

**Reading the numbers.**

- The guides were already cached at 10 %, so dropping 29k characters of them saves most where caching is not
  available (−22 %) and a little with a warm cache (−4.5 %).
- Each distinct guide set costs one small write: 17,911 written tokens against 16,345, that is +1,566 tokens. The core
  prefix is still read by every item.
- The output share of the charge is unchanged (assumed). These are the only percentages claimed. Real cache behaviour
  is visible in production through the 10-18 cache report (`/platform` → "AI cost and cache").

## 2. #12 The one readiness rule at action time

- **The rule.** `packages/engine/src/planItemGate.ts` holds the rule. The engine cannot import analytics
  (dependency boundaries), so analytics registers it: `registerPlanReadinessGate()` (`packages/analytics/src/planGate.ts`)
  registers `plannedItemReadiness` together with the survey's own variable dictionary (`variableMetadata`). A battery
  counts its rows, and a CBC question is known as one.
- **Where it is registered:**
  - the copilot route;
  - the browser's replay on Apply (`lib/copilot/client.ts`), so Apply never stores what the route refused;
  - the plan-edit core (`lib/analysisPlanCore.ts`);
  - the eval harness, through the route and `client.ts`.

  It is kept on `globalThis` under a symbol, so duplicate module copies share it.
- **What is refused.** `add_crosstab`, `add_analysis_test`, `set_analysis_plan` (the item's place is named, e.g.
  `tests[2]`), `update_crosstab` and `update_analysis_test` are refused when an item is not ready. The refusal is the
  rule's own words, for example: "the anova on NPS is not ready to run, so it was not added to the plan — An ANOVA
  compares groups — choose the grouping variable." The one repair call gets that sentence.
- **What is said, not refused:**
  - `propose_analysis_plan` (the engine's own generator) is not refused, because the model cannot repair it. An item
    that is not ready is said in the batch's warnings.
  - An edit that touches none of an already-invalid stored item's inputs (only its priority or reason) is allowed. The
    item's state is said.
- **Stored plans** are never re-checked. They load as before. With no rule registered (engine-only callers), nothing
  changes.
- **Bug fixed on the way.** `update_analysis_test {groupBy: null}` could not clear the grouping: `??` read the null as
  absent.

## 3. #13 Repair for refused MaxDiff / conjoint actions

**Deterministic corrections** (`packages/engine/src/methodRepair.ts` `autoFixMethodAction`; route: no model call, no
charge):

| Refusal | Correction |
|---|---|
| Items per task ≥ the number of items | Items per task becomes the number of items − 1 (≥ 3) |
| Items per task < 3 | 3 |
| Too few tasks to show every item at least once, or to meet the appearances asked for | The fewest tasks that work, but only when the action did not state the tasks (an update that raised the appearances). Stated tasks are the researcher's: more tasks, versions or items per task, or fewer appearances, would each fix it, so the refusal goes to the repair with the reason |
| An item listed twice; a level listed twice | The repeat is dropped |
| Dual-response None together with an in-task None | The None is dropped (dual-response replaces it) |
| More alternatives than the attributes can make different concepts | As many as there are |
| Too few rating profiles (CVA) | The fewest that identify the part-worths |

Each correction goes through the gate and the generator again. It is kept only if more of the batch then applies. It is
said in `reply.assumptions` ("Corrected by the Studio (create_maxdiff): 4 items per task instead of 5 — …") and in
`context.methodFixes`.

**Never invented:**

- missing attributes, levels, items or prices;
- a one-level attribute;
- prohibitions that rule out every concept;
- a `simulate_conjoint` scenario.

`explainMethodRefusal` makes the reason precise. It lists the prohibitions given and says the Studio cannot choose which
to drop. It says "do not invent attributes, levels, items or prices". It says to drop a field another method owns.

**The repair call** now also receives design and analysis-plan actions refused **at the gate**. Before, a turn whose
`create_conjoint` was refused for missing attributes ended with "nothing was changed" and no repair. This covers every
design action: `create/update_maxdiff`, `create/update_conjoint` (CBC, ACBC, menu, CVA, dual-response, labelled) and
`simulate_conjoint`. The methods guide goes with the repair (`repairPrompt`) when the turn did not carry it.

**Still refused after the repair.** The reply ends with a plain note in the researcher's language (`NOTICES.designRefused`;
en, hi, Hinglish, mr, ur): "Note: the MaxDiff / conjoint design could not be made (it was sent back once for correction
and was refused again) — <the reasons>. Nothing was added for it; give what is missing …".

## 4. #14 Script checks beyond patterns

### The tokenizer and reader

`packages/engine/src/scriptAst.ts` has no dependencies.

- **`tokenize`.** Comments and whitespace are dropped. Strings are decoded whatever the quotes. Regex is told apart from
  division. Template literals keep their `${…}` tokens.
- **`normalizedTokens`.** The script's own names are renamed in order of declaration (`$1, $2 …`: `var`/`let`/`const`,
  function names and parameters, arrow parameters, catch). `rs`, globals, properties and object keys are kept.
  Semicolons and block braces are not compared, so ASI and `if (c) x()` versus `if (c) { x(); }` look the same.
- **`similarity`.** The Dice coefficient over 4-token shingles.
- **`readScript`** reads:
  - `rs` calls with their literal arguments;
  - `rs.listen` events, with the option codes a handler filters on (`e.option === "1"`, `String(e.option) == 1`,
    `[…].indexOf(String(e.option))`, `.includes`);
  - the popups it opens, and `closePopup`;
  - the elements it creates or clones, and the HTML it writes;
  - where it mounts them;
  - every style it sets, in every spelling the sandbox lets through: `.style.x = …`, `["style"]["x"]`, a style alias,
    `Object.assign` with a literal or a named object, `setProperty`, `cssText`, `setAttribute("style")`, `style="…"`
    in written HTML, and CSS strings built from concatenated pieces or template literals;
  - attributes, class names and ids.

### (a) Duplicates

`packages/engine/src/uxDuplicates.ts` builds each behaviour's fingerprint:

- the question;
- the trigger, declared or read from the script;
- the guard;
- the popups;
- the effects, or the script's `rs` calls;
- the script.

`refuseDuplicate` in `uxActions.ts` keeps the exact check. It now also refuses:

- **the same popup on the same question** for overlapping answers, written once as a `show_popup` effect and once as an
  `rs.popup` script, or twice as scripts;
- **the same effects** on the same event;
- **a near-duplicate script**: 85 % or more alike after normalisation, on the same event.

The refusal names the behaviour to update: "this repeats a behaviour that is already there — uxb_1 “Q3 option 1 popup”
on Q3: both open a popup on the same question for the same answer. Update uxb_1 instead … (update_behavior …)".

These are different behaviours and are not refused:

- a popup on option 3 next to one on option 1;
- the same script on another event;
- a different guard;
- the effects-and-script pair from one request (production intents, 10-18);
- an update of a behaviour to itself.

Scripts that decide their own event used to have no exact key and were never compared at all.

### (b) Overlays

`overlaySignals` in `uxScriptGuard.ts`, used by `popupProblems`, refuses a script when all of these hold:

- it creates or mounts an element;
- the element is `position: fixed` (in any case);
- the element covers the viewport (inset 0, four zero edges, or 100 % / 100vw × 100 % / 100vh), **or** has a z-index of
  1000 or more, **or** has a translucent backdrop or backdrop-filter, **or** popup words appear in its classes, ids,
  `role="dialog"`, `aria-modal` or its own names.

`position: absolute` counts too when the element covers the viewport and has a z-index of 1000 or more, a backdrop or
popup words.

The element may be mounted anywhere, not only on the body. The refusal now says what it saw ("it sets z-index 99999 and
a dimmed backdrop") and steers to `show_popup` / `rs.popup`.

Not refused:

- a small fixed badge;
- an absolutely placed tooltip inside the card;
- `rs.popup`;
- styles on existing elements.

The runtime gate is unchanged, so stored scripts keep running.

### (c) Popup words in the respondent's language

- **New interface strings** in the survey's translation system (`packages/engine/src/localization.ts`):
  - `popup_close` ("Close");
  - `popup_message` (the name a title-less popup is announced by).

  They are listed for translation **only when the survey has a popup**, and they are optional (never block a launch).
- **The order of precedence.** The survey's translation comes first. Then the built-in text for 35 common languages
  (`BUILTIN_UI_STRINGS`: the Indian languages, Urdu, Arabic, Persian, Hebrew, the main European and East Asian
  languages, Indonesian, Malay, Vietnamese, Thai, Swahili). Then English.
- **A non-English source language** gets the built-in text too. A Hindi survey says "बंद करें".
- **Other languages.** Localization → Translate machine-translates `ui:popup_close` with the existing provider, like
  any element.
- **Popup and message text** (`show_popup`, `show_message`) is now a translatable element (`ux:<behaviour>:<i>:text`
  and `:title`, optional), and `localizeDefinition` shows it in the respondent's language. Text written inside a script
  is not translated. The UX guide now says so and points multilingual surveys to the effects.
- **Right to left.** The popup takes the shell's direction (`dir` on the dialog):
  - its padding uses logical sides, so the close button's room is on the left in Urdu or Arabic;
  - an anchored bubble lines up with its anchor's right edge;
  - `popupUiFor(def, lang)` gives the words and the direction.
- **Wiring.** The runtime passes the respondent's language to the UX layer (`UxLayer language`). The Studio preview
  uses the source language.

### Every existing script still judged the same

`packages/engine/src/fixtures/script-corpus.json` holds 491 scripts found in the repository: the tests, the browser
suites, the guides, the fixtures and the templates. It records the verdict each got **before** this change
(`scripts/engine-11-14/make-script-corpus.mjs`). The test `scriptChecks.test.ts` asserts:

- the runtime gate's verdict is identical for all 491;
- the authoring checks refuse exactly the same scripts.

The only difference is five overlay refusals whose sentence now names what was seen.

## 6. Where to find it

| Feature | Where |
|---|---|
| Per-item guides | Intelligent Mode → paste a brief → Build the plan. Nothing new is shown; the effect is on what is sent. Developers can see `context.itemGuides` and `context.guideMisses` in the `/api/copilot/turn` response (each call's `guides` and `blocks` under `context.sent` with the fake provider). The server log has `guide miss`. `COPILOT_ITEM_GUIDES=off` restores the old behaviour |
| Readiness at action time | Intelligent Mode → "plan an ANOVA of Q1". With no grouping variable the card shows the refusal ("choose the grouping variable") and the repaired item, if any. Data Analytics → Analysis plan never receives the invalid item. The same rule applies to plan edits through `/api/surveys/[id]/analytics/plan` actions |
| Design repair | Intelligent Mode → "Add a MaxDiff of …, 5 per task". The card's assumptions say "Corrected by the Studio …". A design that cannot be made gets the note at the end of the reply. Developers see `context.methodFixes` and `context.repair` |
| Duplicate and overlay checks | Intelligent Mode (or Design with AI) → a second popup or a hand-built overlay. The card's refused list names the behaviour to update or the popup to use |
| Popup words in other languages | The respondent's survey (runtime) or Preview → a popup in a Hindi, Urdu or Arabic survey, or with the language selector. Translate the popup text and "Close" in Studio → Localization → Translations (rows "Behaviour … · popup text" and "Interface · the close button of a popup") |

**Environment variables.** None required. `COPILOT_ITEM_GUIDES=off` is optional and turns off per-item guide selection.

## 7. Not done, and why

- **Real-model behaviour of per-item selection.** It is not measured. A real model may propose actions outside its
  item more often than the scripted replies do; misses are logged so this can be seen.
- **The cache simulation is a model of Anthropic's prefix cache,** not a measurement. Reads and writes in production
  come from the cache report.
- **Item selection is word-based.** It reads English signals and the brief's own words. A Hindi plan item title is
  covered by the fallback only when its kind is "other". Otherwise misses go to the gate and the repair.
- **Strings inside scripts are not translated.** That would need a `rs.t()`-style API. The guide steers multilingual
  popups to effects instead.
- **The tokenizer is not a full JavaScript parser.** Syntax errors remain the runtime gate's to find (`new Function`).
  Data flow is followed one step (a style alias, a named style object), not through functions.
- **Next / Back / Submit labels** are already in the translation system (`branding:buttons:*`). They were not given
  built-in translations, to avoid changing what existing multilingual surveys show.
- **Public docs** (`actions-reference.md`, `capabilities.md`) are stale from other engineers' new actions and
  capabilities, not from this change. Run `node scripts/gen-public-docs.mjs` once their work lands.
