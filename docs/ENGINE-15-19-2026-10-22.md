## #15 Exact even presentation

**Before.** A randomizer's “evenly present” offset the window by the respondent's seed, and a design question's version was `hash(seed) mod versions` — even on average only (1,000 respondents, show 1 of 4: spread 14–62). List Fill's least fill balanced on a snapshot and herded under bursts (spread 17 in bursts of 25).

**Now.** With `randomizer.balance = { exact: true }` or `question.settings.versionBalance = { exact: true }` the arm is **claimed** atomically:

- `rescript_claim_balance(survey, is_test, session, key, arms[], count, basis, hold_seconds)` (0073) locks the slot's key row, expires stale in-progress claims, counts the claims per arm, takes the `count` least-filled arms in the caller's deterministic tie order and records the claim — all under the lock. A burst cannot herd: the next claim cannot count until this one is written.
- **Counted** (`basis`): `completed` (default) = completes + active in-progress claims; an abandoned claim expires after `holdMinutes` (default 120), a screen-out / termination / quota-full / deleted response is released (save route + a trigger on `responses`). `started` = every claim ever made.
- **Tie-break**: `seeded` (per respondent, from the session seed — reproducible) or `sequential` (authored order).
- **Scope**: per randomizer (per loop iteration inside a loop: the key carries the iteration), nested randomizers each their own slot (claimed outer first), per design question; `byQuota` balances within the respondent's cell of that quota.
- **Just in time**: the Runner claims only when the next page to show sits inside an unclaimed exact randomizer (or holds an unclaimed exact design question) — a short “Loading…” card, then the claimed arm. Stored in `state.calculated` (`RANDOMIZER_<ID>` = the child ids shown; `<VAR>_VERSION`), so Back, resume, validation, the renderer, flatten, the CBC stacked file and the MaxDiff long file all read the claimed value.
- **Trust**: the server derives each slot's arms, count and basis from the session's pinned definition; a client-supplied assignment is ignored (re-claimed from the store, which answers a holder with its own arms).
- **Failure**: a claim that cannot be made (no 0073, network) stores the seed-derived arm — the pre-#15 behaviour — and logs it; the respondent never sees an arm change later.
- **Sandbox / preview**: the runtime without a database uses a process-wide `MemoryBalanceStore` (same rules, synchronous = atomic in one JS thread); the preview Runner uses one kept in the tab (sessionStorage, try/catch) — a restart releases the run's claims, a completion completes them, so clicking through a preview shows the arms rotating exactly.

**Default — decided.** Exact balance is **on for new randomizers and new design questions** (ticking “even presentation”, picking a design, Intelligent Mode creating a randomizer with *show N* or a multi-version design) and **off for everything that exists**. It is written into the definition, never a code default, so a survey saved before keeps its seed-derived behaviour, and a running study is pinned to its deployed version anyway — nothing in the field changes. Justification: it is strictly better balance with the same per-respondent stability; its only cost is one small request when a respondent reaches the randomizer, and it degrades to the old behaviour when the database lacks 0073.

**Guarantee, stated precisely.** The counted claims (completed + live in-progress, or every claim for `started`) never differ by more than one between arms, under any concurrency (0 deadlocks: one row lock per slot). The final *completes* can differ by more only through respondents who were counted while in progress and then abandoned — bounded by the abandons open at one time within the hold window.

ACBC has no design versions (concepts are built per respondent), so there is nothing to balance; the version balance applies to MaxDiff, CBC, menu and CVA designs.

## #16 Respondent voice

- **Server fallback** (`SpeechInputButton`, renderer): where the browser has no recogniser (Firefox) — or a test forces it off (`window.__rescriptNoWebSpeech`, `?nowebspeech=1`) — the button records with MediaRecorder (≤ 60 s), asks consent once per session (“Your recording is sent to our transcription service and typed into the box; the audio is not kept.”), shows **Transcribing…**, then **appends** the text through the field's own onChange and gives focus back to the field (caret at the end). When Web Speech fails with an error a server can cure (`network`, `service-not-allowed`, `language-not-supported`), the same press switches to the server.
- **Route** `POST /api/session/dictate` (runtime): the session must be a live in-progress response of a survey whose dictation and server dictation are on for that question; the audio (≤ 4 MB) goes through the existing `transcribe`, metered per minute on the session's project (`respondent_dictation`, SPEECH_TO_TEXT_MINUTE); nothing is stored. A preview may use it only against the fake provider. `GET` says whether the runtime can transcribe — the button appears in server mode only when it can.
- **Grid cells**: matrix_text answers, custom-table text / long-text columns and Editable-Table text columns get a microphone **inside the cell**, visible only while the cell (or the mic) has focus or dictation runs — no column gets wider, no extra tab stop per row; the text goes into that cell's key. Numeric / formatted cells never get one (`speechInputFor` with `{ kind: "cell" }`). Numeric lists keep the existing rule (text fields only).
- **Language**: the question's `speechLang`, then the language the respondent is answering a multilingual survey in, then the voice mode's, the survey's, the browser's — sent to the recogniser and as `x-language` to the server.
- **Switch**: `deployment.speechServer: false` keeps dictation browser-only (Studio → Survey Settings).

## #17 Long recordings and clips

- **Any browser-decodable format** (`lib/qual/browserAudio.ts` + `@rescript/media` `audioChunks.ts`): duration read from metadata first and refused in words above the memory budget (16 kHz float PCM: 64 KB/s per channel; 640 MB ≈ 87 min stereo / 175 min mono); `decodeAudioData` on an **OfflineAudioContext at 16 kHz** (the decoder resamples while decoding, so full-rate PCM never exists; a browser that keeps the file's rate gets an OfflineAudioContext render to 16 kHz mono, then a linear resampler); the encoded bytes are dropped; the PCM is cut into **WAV parts ≤ 24 MB with 2 s of overlap**, each downmixed and encoded only while it is sent (a generator); each part goes to `POST /api/surveys/[id]/qual/recordings/chunk` with its offset, duration and overlaps; parts are retried on a dropped connection and **never paid twice** (a saved project keeps each part's result in `qual_jobs`, key `stt-chunks:<recording>`). Server-side WAV / MP3 splitting is unchanged.
- **Merge** (`mergeChunkTranscripts`): timestamps moved onto the recording's clock; each overlap cut at its midpoint (a word belongs to the part in whose half it starts; a segment straddling a seam is trimmed to that part's words); a phrase both parts heard across the seam with jittered timings is caught by comparing the words at the seam. Without word timings, segments by where they start, said in a warning.
- **Word timestamps**: `transcribe({ words: true })` asks OpenAI-compatible providers for `timestamp_granularities[]=word` (with `segment`) and Google for `enableWordTimeOffsets`; parsed into `words`, present only when returned. Every Studio transcription path asks (single file, server split, browser parts). Stored per segment as `words: [{ s, e, c0, c1, a? }]` (seconds, character span, `a: 1` = interpolated) by `attachWords` / `alignWords` (punctuation and case ignored, split tokens joined, unmatched tokens interpolated and marked).
- **Exact clips**: `excerptClip` — the time range of the excerpt's own words; a transcript without words (or with stale ones) falls back to the turn, and the player says which. Coding (**▶ Play clip**), Highlights and the reel's Word clip list use it; the clip route returns `byWords`. The player seeks, plays and pauses at the end (a 40 ms timer backs `timeupdate`).
- **Corrections keep timings aligned** (`realignAfterEdit`, applied by the transcript-correction route and the sandbox): words outside the edit keep their timings with offsets moved; the corrected words are interpolated across the time the replaced words took (marked approximate); an edit with nothing timed on either side marks the segment's timings stale (clips then play the turn).
- **Sandbox**: “Transcribe a recording in this browser…” works without storage (fake provider); the file stays in the page as an object URL, so its clips play there.

## #18 Reports

- **Section order per document family** (`StructureRequest.sections`, stored in `report_theme_selections.structure` — no migration — or the sandbox tab store): `findings` (findings Word **and** findings deck), `research_plan`, `proposal`, `sap`, `qual` (qualitative Word report **and** qualitative deck). ## #19 Layout at 1024 px

`lib/intelligent/paneLayout.ts` (pure, unit-tested) decides from the workspace's measured width (ResizeObserver): the **conversation keeps ≥ 600 px**; docked panes first shrink toward their minimums (inspector 260, structure 180), then the structure pane becomes a **40 px rail**, then the inspector; below the width where two rails leave less than 600 px (phones) there are no rails and the toolbar buttons open the panes. A rail's button (or the toolbar toggle) opens the pane as a **drawer over the conversation** (takes no width; Escape or × closes). Both panes have **splitters** (pointer; keyboard ← / → 16 px, Shift 64 px, Home / End; `role="separator"` with `aria-valuenow/min/max`), widths remembered in localStorage (`rescript.intelligent`, read in try/catch, clamped). Logical CSS properties: an RTL page mirrors the panes, rails and drawers, and the splitter keys mirror too. The older “one column under 900 / 960 px” rules no longer override the computed columns.

Measured (browser suite): 1440 → conversation 828 px, 1366 → 754, 1280 → 668 (both panes docked); 1024 → 618 (structure as a rail, inspector docked 360; was 418); 768 × 1024 tablet → two rails, 688; 390 → drawers only, 390; no horizontal scroll anywhere; RTL at 1024 mirrored (structure rail on the right).

## Not done / limits

- **Final completes** can differ by more than one only through in-progress respondents who later abandon (bounded by the hold window); the counted claims are exact at every moment.
- A tampered client can mislabel **its own** response's `RANDOMIZER_*` at the final save (the counts stay exact; the claim table is the record of what was assigned).
- Browser decoding is bounded by memory: ~87 minutes of stereo (175 of mono) by default; longer non-WAV/MP3 files are refused in words (split them, or convert to MP3, which the server splits). Decoding depends on the browser's codecs (Chromium without proprietary codecs cannot decode AAC; Chrome, Edge and Safari can).
- Word timings depend on the provider: GPT-4o “transcribe” models answer `json` only and return none (clips then play the turn, said so).
- Respondent dictation records at most 60 s per press; the audio is not stored.
- The live theme preview is a mock page in the theme, not a rendering of the actual document.
- The engine suite's #15 runtime checks run against the sandbox store (same rules as 0073); the database path is proven by the SQL and pgbench tests, not by a browser run against a live Supabase.
- Live Firefox was not available here: the server-dictation path is exercised in Chromium with Web Speech forced off (`window.__rescriptNoWebSpeech`) and a fake microphone.
